# Pattern 1: Changeset Inventory

Catalog every changed file, classify it by domain and change type, and measure the overall size of the changeset. This inventory is the foundation all later patterns build on.

## Goal

Produce a structured table of every changed file with: domain/area, change type, size, and a one-line description of what the change does. Identify files that appear in multiple domains (cross-cutting changes). Flag any generated or derived files that should not drive PR boundary decisions.

## Step-by-Step Process

### Step 1: Gather the raw diff

```bash
# Changed files with status (M=modified, A=added, D=deleted, R=renamed)
git diff main...HEAD --name-status

# Size of each change (insertions/deletions)
git diff main...HEAD --stat

# If working tree has uncommitted changes too, include them:
git diff HEAD --name-status
git status --short
```

If the user provides a PR URL or a specific commit range, use that instead of `main...HEAD`.

### Step 2: Classify each file by domain

For each changed file, assign:

- **Domain:** The business area or architectural layer it belongs to.
  - Use directory structure as the primary signal (`apps/web-app/src/lib/domains/billing/` -> `billing`).
  - Use file naming conventions as secondary signal (`AuthService.ts` -> `auth`).
  - Mark files that span two domains as `cross-cutting`.
- **Layer:** Which architectural layer it sits in.
  - `schema` — .graphql, migration SQL, schema DDL
  - `backend` — Go services, API handlers, route-impl
  - `frontend` — Svelte components, routes, stores
  - `infra` — Kubernetes, Pulumi, Terraform, Dockerfile
  - `config` — .env, Makefile, package.json, CI YAML
  - `test` — test files only (no production code)
  - `docs` — markdown, MDX documentation
  - `generated` — dist/, generated code (do NOT use for boundary decisions)
- **Change type:**
  - `feature` — new behavior
  - `fix` — bug correction
  - `refactor` — no behavior change
  - `chore` — dependency updates, config, tooling
  - `schema-change` — database or API contract change (high impact)
  - `test` — tests only

### Step 3: Build the inventory table

```markdown
## Changeset Inventory

**Branch:** feature/my-large-feature
**Base:** main
**Total files changed:** 47
**Total insertions:** 1,842
**Total deletions:** 634

| File | Domain | Layer | Change Type | +/- Lines | Notes |
| ---- | ------ | ----- | ----------- | --------- | ----- |
| platform-schemas/schemas/billing.graphql | billing | schema | schema-change | +42/-3 | Adds invoice_status field |
| services/web-api/internal/route-impl/billing.go | billing | backend | feature | +187/-12 | Implements invoice status logic |
| apps/web-app/src/lib/domains/billing/... | billing | frontend | feature | +334/-0 | New invoice status UI |
| services/web-db/migrations/sql/20260515...sql | billing | schema | schema-change | +18/-0 | Migration for invoice_status |
| apps/web-app/src/lib/domains/auth/... | auth | frontend | refactor | +45/-67 | Removes deprecated login path |
| ... | | | | | |
```

### Step 4: Identify cross-cutting and generated files

**Cross-cutting files** (appear in multiple domains or serve multiple PRs):
- Shared utilities, design tokens, base components
- Changes to generated outputs (`platform-schemas/dist/`, `*.d.ts` from codegen)
- Package manifest changes (`package.json`, `go.mod`) that support multiple features

Mark these explicitly in the table. They will need special treatment in Pattern 4.

**Generated files** — list them separately and exclude from PR boundary decisions:
```
Generated (exclude from boundary decisions):
- platform-schemas/dist/**  (regenerated by psgen)
- apps/packages/design-system/src/lib/tokens/tokens.*  (if auto-generated)
```

### Step 5: Produce the domain summary

Aggregate the inventory by domain to show the relative weight of each area:

```markdown
## Domain Summary

| Domain | Files | Net Lines | Layers Touched | Primary Change Type |
| ------ | ----- | --------- | -------------- | ------------------- |
| billing | 14 | +589/-15 | schema, backend, frontend | feature |
| auth | 6 | +45/-67 | frontend | refactor |
| design-system | 8 | +212/-34 | frontend, config | feature |
| infra | 3 | +67/-0 | infra | chore |
| cross-cutting | 4 | +28/-12 | config, docs | chore |
```

## Output

Deliver:
1. The full inventory table (all changed files classified).
2. The domain summary table.
3. A list of cross-cutting and generated files to treat specially.
4. A one-line observation about the overall shape: e.g., "Primarily a billing feature with an unrelated auth refactor and infra chore mixed in."

## What to look for

- **Mixed concerns:** Feature code plus unrelated refactors in the same domain -> good split candidate.
- **Schema + logic + UI in one domain:** Classic full-stack feature that deserves its own PR.
- **Isolated domain with small diff:** May be a natural standalone PR regardless of size.
- **Config/chore changes:** Almost always extractable into an independent PR merged first.
- **Test-only changes:** Can often be a separate PR after the logic PR it covers.

## Checklist

- [ ] All changed files listed (use `--name-status` to catch renames/deletions)
- [ ] Each file has domain, layer, change type, and size
- [ ] Cross-cutting files identified and marked
- [ ] Generated files excluded from boundary analysis
- [ ] Domain summary table produced
- [ ] Top-level observation written
